# ANDOR Learn Capture Studio: Gate 1 report

_20 Nov 2026 · branch `feature/learn-capture-studio` · product capture pin `6ef3376`
(`claude/macos-release`, provisional) · review board: `learn/review/` (published copy linked in the
hand-over message)._

## Summary

- **Four pilot demonstrations, seven clips, all captured automatically from the real ANDOR OSP
  editor** — no screen recording, no manual editing. Every scene passed every state assertion and
  every video check on two complete runs.
- **Authentic by construction.** Clicks, key presses, drags and mouse-wheel scrolls are real
  window events through the editor's own peer on a virtual display; audio (MIDI and a live-input
  fixture) runs through the instrument; meters, read heads, arpeggiator steps, STRUM's and
  SATELLITE's displays, the CAPTURE page and the note mapping are OSP's own output. Direct state
  changes are refused inside filmed steps.
- **Validation caught real mistakes.** It is stricter now than when it first passed: one scene
  passed its checks while showing the wrong pattern (a stored index is not the list order); checks
  now read the parameter's displayed text ("CHORD"), and that scene was recaptured correctly.
- **The real-window environment is stable with `-noreset` + a window manager that is waited for:**
  40 further `[popover]` runs, 10 `[menu-visual]` runs and 16 capture runs, no failure.
- **Two honest limitations:** wall-clock-timed UI (analysis duration, toasts) runs about 6× faster
  in the video than in real use; and DAW routing into OSP's Sidechain input is still unverified on
  macOS (the RECORD/GRAB LAST clips show OSP's capture with a deterministic fixture, not a DAW).

## 2. How it works

```
scenario.json ─► osp_learn_capture (test-only; OSP_BUILD_LEARN_CAPTURE, off by default)
                   real OspAudioProcessor + editor on an Xvfb desktop window (openbox, -noreset)
                   set-up: direct state allowed (layers, ARP panel open, input history) — not filmed
                   steps: window events via ComponentPeer (click, key, drag, wheel) or filesDropped
                   per frame: 1600 samples through processBlock (MIDI + input fixture), one
                              message-loop pass, a 2x snapshot (+ menu windows) → lossless master
                   expectations: Learn states, parameter text/values, layers, mapping, recording…
               ─► post.py: one fixed crop per scene, pointer/outline/file badge from the recorded
                   positions, WebM + MP4, poster, step stills, checks, manifest entry
               ─► learn/review/build.py: the comparison page from the manifest
```

Reused, not rebuilt: Learn 2.0 target IDs and states (`osp.source.dropZone`, `osp.source.ready`,
`osp.source.mapped`, `osp.keyboard` …), the ARP panel's public geometry, `binding::findControl`,
the tutorial sounds, the `[capture]` tests' input-bus pattern, the `[menu-visual]` menu
compositing, `SourceDisplay::softwareCaches`. No file under `apps/plugin/Source`, `shared/` or
`src/` changed. Build changes: one `option()` + `add_subdirectory` in the root `CMakeLists.txt`
and `learn/capture/runner/CMakeLists.txt`.

### Editing (as instructed)

One fixed crop per clip (no zoom, no camera moves). A small neutral arrow drawn at the exact
coordinates the runner sent, with a brief ring on press. A thin terracotta outline on the control
about to be used (0.3 s before the click, gone after). The file badge only while the drop travels.
Holds of 0.8–2.4 s around results. **No crossfades:** each clip ends on its final state and the
loop restarts on the first frame (a clean reset). The poster is the stillest frame of the final
hold, without overlays.

## 3. Reliability (investigated before scaling, as asked)

| Test (repo's own real-window tests, `-noreset` + openbox) | Runs | Failures |
|---|---|---|
| `[popover]` with the new wrapper (waits for the window manager to own the screen) | 20 | 0 |
| `[popover]` with the Gate 0 method (openbox, then a fixed 1 s sleep) | 10 | 0 |
| `[popover]` with no wait at all | 10 | 0 |
| `[menu-visual]` with the new wrapper | 10 | 0 |
| Gate 0 total for comparison | 2 | 1 (first-ever run with openbox) |

The Gate 0 failure did not reproduce in 40 further runs. Most likely cause: on the very first
launch openbox builds its configuration and font caches, so the window manager started managing
the editor window while a test was already running (focus changes close popovers). Mitigation in
place: `learn/capture/tools/xvfb-wm.sh` waits until the window manager has registered
(`_NET_SUPPORTING_WM_CHECK`) before starting the runner.

Capture runs: 7 scenes × 2 full runs (after the D2 scenario fix, both runs of the final
scenario), scene A ×4 during development, and a burst of C2 ×3 and D2 ×3 (the two most
asynchronous / interactive scenes): **every run passed**, with identical frame counts for the same
scenario (A 287, B 428, C1 502, C2 343, D1 362, D2 378, D3 389). Pixel comparison of two
independent runs: first and last frames identical; sampled mid-scene frames differ in at most
0.52 % of pixels (mean absolute difference ≤ 0.21 of 255), from wall-clock-timed details.

**Fail-closed behaviour** (`learn/capture/tests/run-negative.sh`): an impossible expectation, a
target that is not shown, and a direct state change inside a filmed step each stop the runner with
the reason and leave no video, poster or manifest entry (`post-report.json` records the failure,
`failure-last-frame.png` the last frame).

**Verdict:** stable enough for unattended production of scenes on this configuration, with two
conditions: (1) the runner stays the gate — a scene is accepted only if every expectation and video
check passes; (2) a human approves each new or changed clip before publication (`approved` stays
false until then).

## 4. Authenticity: what is real, what is drawn, what is disclosed

| Element | Source |
|---|---|
| Interface pixels | the real editor, JUCE software renderer, ceramic look, 2× |
| Clicks, key presses, drags, scrolls | real window events through the editor's peer |
| File import | the editor's own `filesDropped`; the badge is drawn (disclosed in A and B's entries: not an OS drag) |
| Notes | on-screen keyboard clicked with the mouse (A, B, C); a held chord sent as MIDI (D, disclosed) |
| Live input | the input fixture fed into the Sidechain bus block by block (disclosed; DAW routing unverified) |
| Pointer, outline, press ring | drawn in post from the recorded event positions |
| Native dialogs | none shown or simulated |

**Timing (disclosed in every entry):** the capture runs on a frame clock. Everything driven by audio
(meters, read heads, arpeggiator steps, SATELLITE's position, the CAPTURE clock and picture)
moves at true speed. A 2× frame takes about 0.18–0.26 s to render here (×5.4–7.8), so
wall-clock-timed behaviour runs faster in the video: background analysis and note mapping appear
almost instant, and toast notices are brief. Tooltips are switched off for the same reason (a
pointer resting 0.3 s in the video would have rested 2 s in real time).

**Mistakes the process caught and fixed during Gate 1:**
- STRUM scene first selected Thumb Up (stored index 14) while asserting index 14 = Chord. The
  STRUM panel's own message ("STRUM plays with the CHORD pattern") exposed it on review. Fix:
  `paramText` expectations ("CHORD", "DOWN", "UP/DOWN"); recaptured.
- Tooltips appeared in the first arpeggiator captures (slow frames). Fix: suppressed in the runner.
- A forced 16:10 crop cut the arpeggiator scenes' cards; those scenes now use the focus box's own
  aspect.

## 5. Findings for the product (not changed here)

- **CAPTURE A label overlap — reproduced in a real-window render.** On a card's CAPTURE page
  (C2), the card's tool icons draw over the "CAPTURE A" tab label; the empty instrument's page (C1)
  is clean. Still to be confirmed in the standalone app on macOS before it is called a defect
  (listed in `beta-readiness-in-plugin-learn.md`).
- **"Needs review"** is the status OSP shows after mapping both the tutorial phrase and the input
  fixture take ("7 notes · Needs review", "5 notes · Needs review"). The guides must not say the
  result is "Ready".
- SATELLITE's display position comes from the audio engine (`satelliteView`), so its speed in the
  video is real.

## 7. Recommendations for the larger curriculum

1. **Cap the beta site at 12–15 guides** (owner's direction). Proposed set: the four pilots' six
   guides (Load and play, Phrase → MAP NOTES, Record, GRAB LAST, per-layer ARP, STRUM, SATELLITE
   — seven clips), plus One Shot ↔ Granular, Layer sounds, SYNTH & IMPRINT, Custom Patterns,
   KEY DNA, REIMAGINED, USER macro, Save / export. Put RECORD, GRAB LAST, Phrase Transformer,
   per-layer ARP, STRUM and SATELLITE in the homepage's quick access.
2. **One clip per guide, 6–15 s, one idea per step.** D1 carries four ideas in 12 s; it reads, but
   splitting "LINK/EDIT" from "PLAYS" would make each step's still clearer.
3. **Use detail stills for small controls.** At 1600 px the arpeggiator's chips are legible but
   small; a second, tighter step still per step (same frame, cropped) would help on mobile without
   adding camera moves to the video.
4. **Write the guide text from the clip's verified checks.** Each step already has a mark, an
   expectation and a still; Gate 2 can generate the step list from the manifest and attach the
   reviewed copy.
5. **Keep scenes independent and set-up-driven** (as D2/D3 are): a failed scene never blocks others
   and each can be regenerated alone when its `dependsOn` sources change.
6. **Before publishing:** re-pin to the frozen beta UI (PRs #26/#28 if approved), regenerate,
   approve each clip; consider Git LFS or object storage for the videos once the library grows
   (each full regeneration adds ~14 MB of binaries to Git history).
7. **Optional, later:** a "real-time wait" mode for asynchronous steps (duplicate frames while
   analysis runs at wall-clock speed) if realistic waiting times matter for a guide.
