# Custom ARP Patterns — CP3 and CP4: making, editing, keeping

19 November 2026, branch `claude/custom-arp`. CP2 (`03-cp2.md`) put custom patterns into the
one shared arpeggiator. With CP3 the musician can make a pattern: record it, import it, or start
from a factory one, then edit it. With CP4 a pattern is kept: it is embedded in sessions and
presets, saved to a portable library and assigned per card. Everything here is shared code, so
it ships in ANDOR OSP and every ANDOR shell product (ANDOR ANALOG) at once.

## What was built

| Part | Where | What |
|---|---|---|
| Model | `src/model/ArpPatternModel.{h,cpp}` (pure C++) | **Two separate things:** the original take (`CapturedNote`s in quarters, read only) and the editable pattern (`Event`s, each a relative rank or a rest, with a duration in integer ticks: 960 per step, at least 30). `interpret` turns a take into a pattern by RHYTHM (on a 1/2, 1/4 or 1/8 grid) or STEPS (one step per note). A chord inside a phrase keeps one note, and dropped or late notes are reported, never silently lost. `compile` refuses more than 256 events and never truncates. |
| Edits | `arppattern::edit::*` | **Keep the length:** SPLIT, MERGE, EXTEND, REST, DELETE. **Change it, explicitly:** + STEP / - STEP and LENGTH. **Also:** REVERSE, MIRROR, ROTATE, set rank, set mapping. LENGTH never removes a note. `History` keeps 200 steps, one per completed action, and restores exact data. |
| File | `src/io/ArpPatternJson.{h,cpp}` | **Format:** `.andorpattern`, kind `andor.arp-pattern`, `schemaVersion` 1, product-neutral. It holds the id, name, description, the take and its tempo, the interpretation, the pattern and the factory flag. **Refused:** newer schemas, other kinds and invalid patterns. **Rests:** a rest is stored as rank -1, so the rank it carried as a note is not kept. Two rests of the same length and velocity are therefore equal events, and a saved document reloads equal to the one in memory. |
| MIDI import | `readMidiPhrases` | Reads with `juce::MidiFile` and keeps tracks, channels (one part per channel), tempo and PPQ. Velocity-0 note-offs and overlapping notes pair correctly. It runs on a background thread, and a menu picks the part when there are several. |
| Capture | `src/engine/PatternCapture.{h,cpp}` | **Mechanism:** a lock-free SPSC ring of 4096 events, fed from the `midi` buffer **before** the arpeggiator (screen keyboard included). The arpeggiator's output can never be captured, so there is no feedback. **While armed:** every lane's arpeggiator steps aside, so the keys sound as played. It comes back on STOP, CANCEL or closing. **Limits:** 1024 notes per take; past that the take stops and says so. **Audio thread:** no allocation, lock or string. |
| Editor | `shared/andor-ui/Source/CustomPatternEditor.{h,cpp}` | **Form:** a compact contextual panel (`MiniPanel`). **RECORDED:** the take, read only. **PATTERN:** the editing surface (rank rows, step lines, rests dashed, a selection ring; drag a note to change its rank, one undo step). **Keys:** the edit row (SPLIT … REDO) and the action row (PREVIEW; STEPS 1/2 1/4 1/8; CONTOUR DEGREES; LENGTH - +; CLEAR CANCEL USE PATTERN), plus the keyboard (arrows, Delete, s m e r, Cmd-Z / Shift-Cmd-Z). **PREVIEW** plays the pattern on the card as you edit. **CANCEL,** Escape or a click outside puts the card back exactly as it was (its pattern and its CUSTOM). **USE PATTERN** keeps it. |
| Library | `CustomPatternEditor::libraryFolder()` = `~/Documents/ANDOR/Patterns` | **Actions:** SAVE, Rename, Duplicate, Delete, Load, Show folder. **Shared:** one folder for every ANDOR product. **Factory patterns** (`src/model/ArpFactoryPatterns.cpp`, nine, ids `factory.*`) are protected: saving one makes a copy of your own with a new id, and they cannot be renamed or deleted. |
| Panel | `ArpSection` | **The style list ends with:** `Custom: <name>` (CUSTOM on for the card), `Create Pattern...` and `Custom Patterns...` (load, edit, factory). **Double-click** the custom row to edit. **Selection:** choosing a style turns CUSTOM off and keeps the card's pattern, ready to come back. **The PATTERN picture** shows the custom pattern's whole length, its ranks and `N STEPS`. |
| Per card | `ArpSection::customCard()` | **Linked:** card A's pattern (every linked lane plays it). **Unlinked:** the card being edited (EDIT A / B / C), each with its own pattern and CUSTOM. |
| State | `InstrumentHost::customPatternsToXml / FromXml` | **In both processors' state:** `<CustomPatterns schema="1"><Card index json/></CustomPatterns>`, holding each card's whole document. Presets and portable instruments (`preset.xml`) are the same state, so they embed it too. **Absent:** every card has none; it is written only when a card has a pattern, so an older session reads as it did. **An unreadable document** (for example a newer schema) is skipped and reported; the rest of the state loads. |

## Decisions

- **Patterns are embedded, not referenced.** A session or preset holds the whole document
  (take included, a few KB). Deleting, renaming or moving the library file, or opening the
  session on another computer, changes nothing. The library is for reuse, not for recall.
- **Loading a state replaces every card's pattern,** as USER MACROS do. A starting state or a
  preset without patterns clears them, because a preset is a whole sound.
- **The panel shows one selector.** CUSTOM is one more row in the style list, as the CP0 audit
  recommended. `arp.pattern` is unchanged, so automation keeps its meaning.
- **Recording starts at the first note** (its tempo is the take's). The editor offers RHYTHM
  on a grid or STEPS; the take is never changed, only re-read.

## Guarantees and their tests

**`[arp-pattern]`** (`tests/unit/ArpPatternModelTests.cpp`, 6 cases) covers:
- a capture becoming the lab's pattern in RHYTHM and STEPS;
- reported drops;
- edits that keep or change the length as they say;
- undo and redo to exact data;
- limits (minimum subdivision, capacity, LENGTH never removing notes);
- the file round trip and refusals;
- MIDI import (tracks, channels, tempo, PPQ, velocity-0 note-offs, overlaps).

**`[arp-custom-ui]`** (`tests/plugin/CustomPatternUiTests.inc`) covers:
- **Recording:** recording plays the keys as played, not arpeggiated. The capture holds exactly the notes played, with their onsets and lengths. The arpeggiator returns after STOP. CANCEL clears the take.
- **No allocation** on the audio thread while recording.
- **Editing:** a take becoming a pattern; every action is one undo step, and the keys sit in place without overlaps.
- **PREVIEW, CANCEL and USE:** they act on the card exactly as described, on card B too.
- **Import and library:** MIDI import with two parts picks one. The library saves, renames, duplicates and deletes. A factory save makes a copy.
- **Panel:** the ARP list's custom rows, choosing CUSTOM and choosing a style.
- **Factory patterns:** valid, marked factory and distinct.

**`[arp-custom-state]`** (`tests/plugin/CustomPatternStateTests.inc`) covers:
- **Session recall:** the whole document round trips exactly, is handed to the audio thread and saves identically again.
- **Older states:** a state without patterns clears them.
- **Bad documents:** an unreadable document is skipped while the rest loads.
- **No library dependency:** a preset and a session both play their pattern after the library file is deleted.

**`[shell][arp-custom]`** (`tests/shell/ShellTests.cpp`, built per product) covers:
- state and preset recall in ANDOR ANALOG and the example product;
- an older state clearing every card's pattern;
- recording offered exactly where the product runs the arpeggiator.

**Screenshots:** the hidden `[custom-arp-shots]` test writes the editor (empty, after a take,
split and previewing) and the ARP panel with a custom row (`OSP_CUSTOM_ARP_SHOTS=<dir>`).

## Pack authoring (investigated, not built)

- **What packs already carry:** a pack's presets are states, so a custom pattern used by a pack
  preset already ships inside it, with nothing extra to build. The pack builder copies
  `.osppreset` files whole.
- **What packs do not carry:** library patterns on their own, as a "pattern pack". That would
  need:
  - a `patterns/` folder in the pack format;
  - an install step into the library;
  - the factory flag set on publish, so they are protected like the built-in nine.
- **Status:** none of this is needed for a preset to work. It is listed under NEXT.

## Not in CP3 / CP4

- **Pattern packs:** library patterns distributed on their own (above).
- **Velocity and microtiming editing (CP6):** each event already carries and plays its captured velocity, but the editor does not draw or edit it.
- **Real DAWs and real performances:** host tests, and listening with real takes.
